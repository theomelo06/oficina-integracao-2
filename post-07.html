Semana 7 — Desenvolvimento do front-end e back-end

Nesta etapa, começamos a desenvolver a aplicação que será usada para fazer os pedidos. Dividimos o software em duas partes: o front-end, com a interface que aparece para o usuário, e o back-end, responsável por receber e conferir os dados da receita.

Montando a interface

O front-end foi organizado na pasta BEBER-front, usando HTML, CSS e JavaScript no VS Code. A primeira versão tem uma proposta simples: permitir a escolha dos ingredientes e enviar o pedido pelo botão de preparo.

A interface reúne campos para as quantidades de whey, leite em pó e água, além da seleção entre cinco sabores: chocolate, morango, baunilha, cookies e morango com chocolate. Também reservamos um espaço para mostrar mensagens sobre o envio do pedido e possíveis erros.

Neste início, a prioridade é deixar o fluxo fácil de entender. O usuário precisa conseguir selecionar a receita, conferir as quantidades e saber se o pedido foi aceito.

Criando a API

Para o back-end, começamos uma API em C# com ASP.NET Core, desenvolvida no Visual Studio. O projeto ficou separado na pasta BEBER.Api, dentro do mesmo repositório da aplicação.

Criamos uma rota para receber a receita personalizada. Ao clicar em preparar, o JavaScript reúne os valores do formulário e envia uma requisição HTTP com os dados em JSON. A API recebe essas informações e as transforma em um objeto que pode ser validado pelo código em C#.

Conferindo o pedido

A validação é importante para impedir que valores inválidos sigam para a máquina. Entram nessa conferência as quantidades dos ingredientes, o volume de água e o sabor selecionado. Quando algum valor não atende às regras, a API deve devolver uma mensagem que ajude o usuário a corrigir a receita.

Também precisamos diferenciar as etapas: receber uma receita na API não significa que a bebida está pronta. A confirmação do preparo dependerá das informações enviadas pelo ESP32 durante a execução.

Preparando a comunicação com a máquina

A API será a ligação entre a interface e o ESP32. Depois de conferir a receita, ela deverá encaminhar os dados ao firmware pela rede Wi-Fi local e tratar a resposta recebida.

Essa divisão permite trabalhar na interface e nas regras do pedido antes de ter todos os componentes físicos funcionando. Por enquanto, o foco está no caminho entre formulário, requisição e resposta.

Próximos passos

Vamos melhorar as mensagens da interface, testar receitas válidas e inválidas e preparar a integração com o firmware. A ideia é manter o formato dos dados bem definido para que a API e o ESP32 entendam o mesmo pedido.
